Security

Org-Wide Defaults always come first — they set the baseline (Private, Public Read Only, Public Read/Write). Role Hierarchy can only open access further from there, never restrict it.
When you need to grant extra access to a subset of users without cloning an entire profile. Permission Sets are additive and much easier to reason about individually.
No. Sharing Rules can only widen access, never narrow it. If OWD is Public Read/Write, a Sharing Rule can't make it more private.
Object-level security decides if a user can see the tab or object at all. Field-level security is more granular — a user might see the Opportunity but not its Amount field.
Programmatic sharing created via Apex, used when the sharing logic is too complex for declarative sharing rules — often tied to custom business logic that changes record ownership dynamically.
A Permission Set Group bundles multiple Permission Sets into one unit, so you can grant a whole stack of permissions in a single assignment instead of assigning each set individually. It makes it much easier to manage access for roles that need a combination of permissions spread across several sets.
Manual Sharing is a one-off, record-level grant made by the record owner or an admin. Sharing Rules are automatic and criteria-based, applied consistently across all matching records. Manual shares also disappear when the record owner changes, so Sharing Rules are the sustainable choice for anything ongoing.

Think of it as a funnel. Org level (login hours, IP ranges, MFA), then object level (profiles and permission sets), then field level (field-level security), then record level (OWD, role hierarchy, sharing rules, manual sharing, Apex sharing). A user needs to clear every layer to see a value.

View All and Modify All (object permissions) override sharing for one object only. View All Data and Modify All Data (system permissions) do it for every object. Because they bypass sharing completely, grant them sparingly, ideally through permission sets and only for integration users or true admins.

A Permission Set, or a Permission Set Group assigned to that user, adds the access. Permissions are the union of the profile and every permission set. If you need to take something away within a group, use a muting permission set.

A special permission set that lives inside a Permission Set Group and switches off specific permissions granted by other sets in that group, only for the group. It lets you reuse a standard set of permissions and remove a couple of items without cloning anything.

Access Salesforce grants automatically along relationships. Access to an Account's child records gives access up (a user who can see an Opportunity can see its parent Account in a limited way), and access to a parent can give access down to child records such as Contacts, Opportunities and Cases, depending on the role and settings. You can't turn it off.

Restriction rules are real security: they limit which records a user can see even if sharing would allow it, such as hiding records marked confidential from contractors. Scoping rules only narrow the *default* view (list views, reports, search), but users can still reach other records they have access to through other means, so they aren't a security control.

Give guests the least access possible. Guest users get records through guest sharing rules only, can't be given View All or Modify All, and shouldn't see sensitive objects. Use sharing sets and sharing rules for authenticated external users. Review the guest user profile after every release.

Apex runs in system mode by default, so you opt in. Use WITH USER_MODE in SOQL (or AccessLevel.USER_MODE in Database methods) to enforce the running user's CRUD, FLS and sharing. Older options are WITH SECURITY_ENFORCED, Security.stripInaccessible() and the isAccessible() describe checks.

Yes. Salesforce requires MFA for direct logins to the UI, and you can meet it with a TOTP authenticator app, a security key or built-in biometrics. SSO logins can satisfy MFA through the identity provider. Treat MFA as the baseline and layer IP and session controls on top.

SAML is for authenticating users into an app, which gives single sign-on. OAuth is for authorising an app to access resources on a user's behalf without sharing a password, which is what API integrations use. Salesforce can be an identity provider (SAML) as well as an OAuth provider.

Platform Encryption (part of Shield) encrypts data at rest, including standard fields, files and attachments, using keys you control, and it keeps most platform features working. Classic encrypted fields are a custom field type with a masking feature and many limitations. Choose Shield when compliance rules require real encryption at rest.

Flow replaces both. Record-Triggered Flows cover every Workflow Rule scenario, and Autolaunched or Screen Flows handle everything Process Builder used to do. If an org still has either running, they're on borrowed time — Salesforce no longer supports them and won't be creating fixes.
A Scheduled Path lets the flow run additional logic at a set time after the trigger event — for example, sending a follow-up notification 3 days after a case is opened without a response. It's the Flow equivalent of a Workflow Rule's time-dependent action, without needing a separate scheduled flow.

Record-Triggered runs when a record is created, updated or deleted. Screen Flow guides a user through a UI. Autolaunched has no UI and is called from other flows, Apex or buttons. Scheduled-Triggered runs on a schedule for a batch of records. Platform Event-Triggered reacts to events. Orchestration coordinates multi-step, multi-user processes.

Never put Get Records, Create, Update or Delete elements inside a loop. Collect the records into a collection variable in the loop, then do one Update or Create after it. Flows run under the same governor limits as Apex, so the same rule applies: one query and one DML for the whole set.

Add Fault paths to elements that can fail (DML, Apex actions, callouts) and route them to a Screen, a Create Records element that writes to an error log object, or an email to admins. Without a fault path the flow fails, the user sees a generic error, and the transaction rolls back.

When logic needs complex data transformations, heavy bulk processing, callouts with detailed error handling, or when you need unit tests as a safety net. Choose Flow when it's a straightforward rule that admins will maintain. Often the answer is both: Flow for orchestration and an invocable Apex action for the tricky part.

It can only change fields on the record that triggered it. It can't create or update other records, send emails or run callouts, and it can't use some actions that need a saved Id. Use an after-save flow for those. Before-save is the fastest, so use it whenever you're just setting fields.

Use Debug in Flow Builder (with the option to run as a specific user and with rollback), check the Flow Interview in Paused and Failed Flow Interviews, read the fault email Salesforce sends to the last editor, and use Apex Debug Logs when the flow calls Apex. A subflow is a flow called from another flow. It lets you build a reusable piece of logic once (for example "create audit log entry") and call it from many places, so a change happens in one place. Keep inputs and outputs explicit.

Anything unsupported (certain outbound messages, time triggers with special logic) has to be rebuilt by hand. Entry conditions decide whether the flow starts at all. You can also choose to run only when a record is updated to meet the conditions, so the flow doesn't fire again on every save of a record that already matched. Tight entry conditions are the easiest way to avoid performance problems and unwanted loops.

Before triggers are for changing fields on the records being saved (no extra DML needed) and for validation with addError(). After triggers are for work that needs the record's Id or must touch other records, such as creating child records. Records in Trigger.new are read-only in an after trigger.

Use a static variable in a helper class, such as a Set<Id> of records already processed, and skip those on later passes within the same transaction. A single static Boolean is risky because it blocks legitimate second passes on other records. Better still, only update when a field really changed.

A List is ordered and allows duplicates, indexed by position. A Set is unordered and unique, perfect for collecting Ids for a WHERE Id IN :ids query. A Map holds key-value pairs, and new Map<Id, Account>(accountList) builds a lookup by Id in one line.

The DML statement is all-or-nothing: one failure throws an exception and the whole operation rolls back. Database.insert(records, false) allows partial success and returns a SaveResult for each record so you can read the errors and carry on with the rest.

Async Apex & testing

  • Future methods: fire-and-forget, static, primitive parameters only. Fine for a simple callout or a mixed-DML workaround.
  • Queueable: like future, but accepts objects, returns a job Id, and can be chained. The default choice today.
  • Batch Apex: processes large data sets in chunks (default 200 records per execute).
  • Schedulable: runs a class at a set time, often to kick off a batch.

A Queueable job can take complex parameters (sObjects, collections, custom types), returns a job Id you can monitor, supports chaining one job from another, and can have a Finalizer for cleanup. Future methods accept only primitives and can't be chained or monitored.

start() returns the records to process (a QueryLocator can cover up to 50 million rows, or an Iterable), execute() runs once per chunk with its own governor limits, and finish() runs once at the end for follow-up work like sending a summary email or chaining another batch.

Each execute() is a separate transaction, and instance variables are reset between them. Database.Stateful keeps your member variables (such as a running total or an error list) alive across chunks, so finish() can use them. It uses more memory, so keep the state small.

If your execute() uses a plain DML statement and one record fails, the exception rolls back that chunk's transaction (all 200), and the next chunks still run. If you use Database.update(scope, false), only the failing record is skipped and you can log its error.

The default is 200, and the maximum is 2,000. Reduce it when each record triggers heavy processing or callouts (limits apply per chunk), and raise it only if the work per record is very light. Smaller scopes also reduce record-lock conflicts.

Implement Schedulable and call System.schedule('Job name', cronExpression, new MyJob()), or use the Schedule Apex button in Setup. A cron such as 0 0 2 * * ? means 2 AM every day. Keep the schedulable thin and have it launch a batch or Queueable.

Not directly, because callouts can't run while the transaction holds uncommitted DML. Hand the work to an asynchronous method (Queueable with Database.AllowsCallouts, or a Platform Event with a subscriber) and make the callout there.

A class that implements Finalizer and is attached with System.attachFinalizer(). It runs after the job finishes, whether it succeeded or threw an exception, so it's the right place to log failures or re-enqueue a retry.

Setup, Apex Jobs, shows status and errors for batch, future and Queueable jobs. Scheduled Jobs shows what's scheduled. In code, query AsyncApexJob using the job Id. Debug logs can be turned on for the user who runs the job.

Create your own test data (don't rely on org data), test positive, negative and bulk cases (200+ records), use System.assert/Assert methods to check outcomes, and test as different users with System.runAs. Coverage is the by-product, not the goal. 75% is the deploy minimum, and every trigger needs some coverage.

They mark the code you're testing and give it a fresh set of governor limits, separate from the data setup above. Any asynchronous Apex you queued inside them runs synchronously when stopTest() is called, so you can assert on the result right after.

It marks one method that creates shared test data once for the whole class. Each test method then sees the data in its original state, because changes made by one test are rolled back before the next. Only one @testSetup method is allowed in a class.

Tests can't make real callouts. Implement HttpCalloutMock (or use StaticResourceCalloutMock) and call Test.setMock(HttpCalloutMock.class, new MyMock()) before the code under test. For SOAP, implement WebServiceMock.

Almost never. By default tests can't see org data, which keeps them repeatable. Use SeeAllData=true only for the few things that really need it, since a test that depends on specific production data will break as soon as that data changes.

Use System.runAs(user). It enforces that user's record sharing and permissions in the block, and it also lets you work around mixed DML. It doesn't enforce field-level security unless the code under test does (for example with WITH USER_MODE).

Typical reasons: validation rules, required fields or flows in production that the test data doesn't satisfy, tests that rely on SeeAllData or on specific records, hard-coded Ids, different record types, or tests that depend on run order. Make test data self-contained and run all local tests in a full sandbox before the release.

Lightning Web Components

Three files with the same name: an HTML template, a JavaScript class, and an optional CSS file, plus a .js-meta.xml file that says where the component can be used (record page, app page, Flow screen, and so on). LWC uses standard web components, with Salesforce-specific modules such as lightning/uiRecordApi.

@api makes a field or method public so a parent can set it. @wire connects to a data service or Apex method reactively. @track is only needed to watch deep changes inside objects and arrays, because all fields are reactive by default, and you rarely need it now.

constructor(), connectedCallback() (inserted into the DOM, good for loading data), renderedCallback() (after each render, can run many times), disconnectedCallback() (removed, clean up listeners), and errorCallback() (catches errors from child components).

Parent to child: public @api properties and methods. Child to parent: a CustomEvent that the child dispatches and the parent handles. Unrelated components: Lightning Message Service (publish and subscribe over a message channel) or a pub-sub module. Use the simplest option that fits.

@wire is declarative and reactive: it re-runs when its parameters change and the platform caches results (the Apex method needs cacheable=true). Use imperative calls when the action is user-driven, needs to run DML, or when you want full control of when it executes.

Cacheable methods may be cached on the client and re-run silently, so they must be read-only. For writes, use a non-cacheable method called imperatively, or lightning/uiRecordApi functions like updateRecord. Use refreshApex() afterwards to refresh cached wire results.

Declare @api recordId; on a component placed on a record page. Salesforce sets it automatically. For the object, use @api objectApiName. To fetch field values, use getRecord with the Id and a list of field imports.

Base components built on Lightning Data Service that give you forms without Apex. record-form is the quickest (one tag), record-edit-form lets you control layout and handle save events, and record-view-form shows read-only fields. All respect the user's field-level security.

A client-side layer, comparable to a cache, that loads, creates, edits and deletes records without Apex. It shares data between components, respects CRUD and FLS and keeps components consistent when a record changes. Wire adapters like getRecord use it.

Dispatch a ShowToastEvent from lightning/platformShowToastEvent. For navigation, use NavigationMixin with a page reference (record page, object list, web page). It's the supported replacement for old URL hacking.

Use lwc:if, lwc:elseif and lwc:else on a template or element. The older if:true and if:false directives still work but are being replaced. For lists, use for:each with a unique key on each item.

Salesforce's modern security architecture for Lightning components, replacing Lightning Locker. SOQL & data

Child to parent uses dot notation: SELECT Name, Account.Name, Account.Owner.Name FROM Contact. Parent to child uses a subquery on the relationship name: SELECT Name, (SELECT LastName FROM Contacts) FROM Account. For custom relationships, the name ends in __r.

A semi-join filters with a subquery on IN: WHERE AccountId IN (SELECT AccountId FROM Opportunity WHERE IsWon = true). An anti-join uses NOT IN for the opposite: accounts with no won opportunities.

You can use COUNT(), SUM(), AVG(), MIN() and MAX() with GROUP BY and filter groups with HAVING. The result is a list of AggregateResult objects, and you read values with ar.get('alias'). Always alias aggregates so you can read them.

for (Account a : [SELECT Id FROM Account]) retrieves records in batches of 200 internally, instead of loading everything into memory, so it avoids heap-size errors on large result sets. It's the right choice when you only need to process rows once.

LIMIT caps how many rows return. OFFSET skips rows for paging, but it has a maximum of 2,000, so it isn't suitable for deep paging. For big sets, page with a keyset: remember the last Id and query WHERE Id > :lastId ORDER BY Id LIMIT 200.

A query whose filter uses an indexed field and returns a small enough fraction of the records for Salesforce to use the index. Non-selective queries on large objects time out. Avoid leading wildcards, negative operators (!=, NOT IN) and functions on the filtered field, and check the Query Plan tool in the Developer Console.

Add ALL ROWS in SOQL (or queryAll in the API) and filter on IsDeleted = true. Records in the Recycle Bin remain for 15 days, after which they're removed for good unless you've exported them.

It locks the returned rows for the duration of the transaction, so other transactions can't change them. It prevents race conditions but can cause lock contention, so use it sparingly and keep the transaction short.

A clause for polymorphic fields like Who or What on Task. It lets you query different fields depending on the object type: SELECT TYPEOF What WHEN Account THEN Phone WHEN Opportunity THEN Amount END FROM Event.

SOSL searches text across several objects at once and returns a list of lists of records. It's limited to text, email and phone fields, returns up to 2,000 rows, and can be used in triggers and classes. Use it when you need a search box, and SOQL when you know the object.

The Import Wizard is browser-based and friendly, with a limit of 50,000 records per import, and supports Accounts, Contacts, Leads, Campaign Members and custom objects, but not Opportunities. Data Loader is a desktop and command-line tool that handles up to 5 million records, can export, update, upsert and delete, and can use the Bulk API.

Put the parent's External ID in the child's CSV (for example Account.External_Id__c) and use upsert. Salesforce resolves the parent by that value, so you don't need Salesforce IDs. This also makes loads re-runnable, because existing records are updated instead of duplicated.

Sort the load file by parent Id so batches don't fight over the same parent, use smaller batch sizes or the Bulk API's serial mode, avoid data skew, and defer sharing recalculation or triggers while loading when it's safe to do so.

Filters that aren't selective, too many cross-object fields, formula fields in filters, and very large objects with skew. Add indexed filters (such as date ranges or an External ID), ask for a custom index from Salesforce Support if needed, and consider archiving old data.

Design patterns & SOLID

A design pattern is a named, proven shape for a problem that keeps coming back, like "create objects without hard-coding the class" (Factory). In Apex they matter because governor limits punish messy code at scale, many developers share one org, and tests are mandatory, which is hard when classes build their own dependencies. A shared vocabulary also makes code reviews faster: "this should be a Strategy" says a lot in four words.

  • Single Responsibility: a class has one job and one reason to change.
  • Open/Closed: add behaviour by adding code, not by editing old code.
  • Liskov Substitution: a subclass must work anywhere its parent is used.
  • Interface Segregation: prefer small interfaces to one big one.
  • Dependency Inversion: depend on abstractions, and pass the concrete pieces in.

Each class should have one job. A trigger that validates, queries, calls an API and sends email has four reasons to change, so any edit risks the other three. Keep the trigger itself to one line that hands over to a handler, and move each concern into its own class (service, selector, callout wrapper). You can unit test each piece alone.

A Singleton guarantees one instance, normally with a private constructor and a static getInstance(). In Apex, static variables live for one transaction only, so the instance is shared within a single save or request but never between users or transactions. Use it as a per-transaction cache (for example, reading Custom Metadata once instead of ten times). For sharing across transactions, use Platform Cache.

public class AppConfig {
    private static AppConfig instance;
    private AppConfig() { /* load settings once */ }
    public static AppConfig getInstance() {
        if (instance == null) { instance = new AppConfig(); }
        return instance;
    }
}

A factory decides which concrete class to create so callers only ask for what they need. To make it admin-configurable, store the class name in a Custom Metadata record and load it with Type.forName(name).newInstance(), casting to the interface. New behaviour then means a new class plus a metadata record, with no change to the factory.

Type t = Type.forName('SmsNotifier');
Notifier n = (Notifier) t.newInstance();

A Builder constructs a complex object step by step through readable methods and finishes with build(), which can validate the result. In Salesforce it shines in two places: building callout request bodies with many optional parts, and test data builders (new ContactBuilder().withLastName('Lee').build()), which keep tests short and intention-revealing.

Strategy puts each algorithm behind the same interface so the caller can swap them at run time (pricing, discounts, lead routing). It satisfies Open/Closed: a new algorithm is a new class, and existing, tested code is not edited. It replaces long if / else if chains on a type string that grow every sprint.

Anywhere a parent type is used, a subclass must behave correctly. If a virtual method on a base trigger handler logs and validates and a subclass overrides it and skips both, callers get surprises. The classic sign is an override that just throws "not supported". The fix is usually to put the capability in an interface that only the classes that really support it implement.

Database.Batchable, Schedulable, Queueable and Comparable are small, separate interfaces. A class opts in to just the behaviour it needs instead of implementing one giant "AsyncJob" interface with methods it would have to fake. Follow the same idea in your own code: if implementers have empty or throwing methods, split the interface.

High-level code depends on an interface, and the concrete implementation is passed in (constructor injection) instead of created with new inside. In a test you inject a fake. Salesforce supports the idea directly: HttpCalloutMock replaces real callouts, and the System.StubProvider API lets you stub classes without hand-writing fakes.

public class OrderProcessor {
    private PaymentGateway gateway;
    public OrderProcessor(PaymentGateway gateway) { this.gateway = gateway; }
}

Use an interface for a pure contract with no shared code, and when unrelated classes should be interchangeable. Use an abstract class when subclasses share code but must fill in some methods (Template Method). Use a virtual class when the base is usable on its own but subclasses may override parts. Prefer interfaces plus composition over deep inheritance, since a class can implement many interfaces but extend only one class.

With Observer, a publisher notifies registered listeners without knowing them. An in-code version runs inside the same transaction, so the listeners share its limits and a failure can roll everything back. Platform Events are the platform-scale version: asynchronous, durable, and usable across transactions, orgs and external systems. Use in-code listeners for small in-process hooks, and events when the reaction can happen later or elsewhere.

Database.Batchable is a template: the platform fixes the order (start, then execute per chunk, then finish) and you fill in the steps. You can add your own layer with an abstract base batch class that handles logging, error collection and retries once, and leaves only process(records) for subclasses to implement.

A Unit of Work records every record you intend to insert, update or delete (registerNew, registerDirty, registerDeleted) and writes them together in a single commitWork(). It orders DML correctly across relationships, keeps you inside DML limits by batching per object, and rolls back everything if one step fails. The fflib library's fflib_SObjectUnitOfWork is the common implementation.

A layered architecture popularised by fflib Apex Common. Selectors hold all SOQL for an object (and enforce field security). Domain classes hold rules about one object's records, typically trigger logic. Services hold business processes that span objects and use selectors and a unit of work. Controllers, triggers and flows call services, so logic is written once and reused everywhere.

Three common routes. For callouts, implement HttpCalloutMock and call Test.setMock. For your own classes, program to an interface and inject a hand-written fake. Or use the System.StubProvider interface with Test.createStub(), which builds a stand-in at run time so you control return values without writing a fake class for each dependency.

Patterns add classes, indirection and stack depth. A Factory with one product, or an interface with one implementation and no tests, is noise. Add a pattern when you feel a concrete pain: a growing if / else, a class you cannot test, the same logic repeated in three places. Keep each pattern simple, name classes for the pattern (PercentOffStrategy), and prefer composition to inheritance.

Define an interface (for example OutboundHandler.process(request)), store one Custom Metadata record per integration with the class name, endpoint (Named Credential) and settings, and load handlers with a Factory using Type.forName. Wrap handlers with Decorators for logging, retries and error capture, trigger work through a Queueable or Platform Event, and keep every credential in Named Credentials. Adding an integration is then a class plus a metadata record.

Coding exercises

Collect the affected Account Ids in the trigger, then recalculate with an aggregate query in a helper, so it's bulk-safe and handles insert, update, delete and undelete.

trigger ContactTrigger on Contact (after insert, after update, after delete, after undelete) {
    Set<Id> accountIds = new Set<Id>();
    for (Contact c : (Trigger.isDelete ? Trigger.old : Trigger.new)) {
        if (c.AccountId != null) accountIds.add(c.AccountId);
    }
    if (Trigger.isUpdate) {
        for (Contact c : Trigger.old) {
            if (c.AccountId != null) accountIds.add(c.AccountId);
        }
    }
    ContactRollup.recalculate(accountIds);
}

public class ContactRollup {
    public static void recalculate(Set<Id> accountIds) {
        Map<Id, Integer> counts = new Map<Id, Integer>();
        for (AggregateResult ar : [
            SELECT AccountId a, COUNT(Id) c FROM Contact
            WHERE AccountId IN :accountIds GROUP BY AccountId
        ]) {
            counts.put((Id) ar.get('a'), (Integer) ar.get('c'));
        }
        List<Account> toUpdate = new List<Account>();
        for (Id accId : accountIds) {
            toUpdate.add(new Account(
                Id = accId,
                Number_of_Contacts__c = counts.containsKey(accId) ? counts.get(accId) : 0
            ));
        }
        update toUpdate;
    }
}

        if (String.isBlank(c.Email)) continue;
        String key = c.Email.toLowerCase();
        if (existing.contains(key) || !seen.add(key)) {
            c.Email.addError('A contact with this email already exists.');
        }
    }
}

Only act when the stage actually changed, and collect the updates in a map so each Account is updated once.

trigger OppRating on Opportunity (after insert, after update) {
    Map<Id, Account> toUpdate = new Map<Id, Account>();
    for (Opportunity o : Trigger.new) {
        Boolean becameWon = o.StageName == 'Closed Won' && o.AccountId != null
            && (Trigger.isInsert || Trigger.oldMap.get(o.Id).StageName != 'Closed Won');
        if (becameWon) {
            toUpdate.put(o.AccountId, new Account(Id = o.AccountId, Rating = 'Hot'));
        }
    }
    update toUpdate.values();
}

Find the accounts whose field really changed, query their contacts once, and update them in one DML.

trigger AccountCitySync on Account (after update) {
    Set<Id> changed = new Set<Id>();
    for (Account a : Trigger.new) {
        if (a.BillingCity != Trigger.oldMap.get(a.Id).BillingCity) changed.add(a.Id);
    }
    if (changed.isEmpty()) return;
    List<Contact> toUpdate = new List<Contact>();
    for (Contact c : [SELECT Id, AccountId FROM Contact WHERE AccountId IN :changed]) {
        c.MailingCity = Trigger.newMap.get(c.AccountId).BillingCity;
        toUpdate.add(c);
    }
    update toUpdate;
}

Implement Database.Stateful so the counter survives between chunks.

public class ColdLeadBatch implements Database.Batchable<SObject>, Database.Stateful {
    private Integer processed = 0;

    public Database.QueryLocator start(Database.BatchableContext bc) {
        return Database.getQueryLocator([
            SELECT Id, Rating FROM Lead
            WHERE IsConverted = false AND LastActivityDate < LAST_N_DAYS:90
        ]);
    }
    public void execute(Database.BatchableContext bc, List<Lead> scope) {
        for (Lead l : scope) l.Rating = 'Cold';
        Database.update(scope, false);
        processed += scope.size();
    }
    public void finish(Database.BatchableContext bc) {
        System.debug(processed + ' leads marked Cold');
    }
}
// Run it: Database.executeBatch(new ColdLeadBatch(), 200);

public class SyncJob implements Queueable, Database.AllowsCallouts {

        req.setMethod('POST');
        req.setHeader('Content-Type', 'application/json');
        req.setBody(JSON.serialize(ids));

        }
    }
}

public static List<SObject> search(String objectName, String term) {
    if (!Schema.getGlobalDescribe().containsKey(objectName)) {
        throw new IllegalArgumentException('Unknown object: ' + objectName);
    }
    String soql = 'SELECT Id, Name FROM ' + String.escapeSingleQuotes(objectName)
                + ' WHERE Name LIKE :pattern LIMIT 50';
    Map<String, Object> binds = new Map<String, Object>{ 'pattern' => '%' + term + '%' };
    return Database.queryWithBinds(soql, binds, AccessLevel.USER_MODE);

Behavioral & career

Pick one real story and use the STAR shape: the Situation (what was the business problem), your Task, the Actions you took (how you diagnosed and fixed it) and the Result (a number if you have it). Good topics are a performance problem, a data migration, or a bad deployment. Interviewers care about how you debug and communicate more than the exact bug.

Start with the simplest tool that is maintainable: validation rules, Flow and standard features first. Move to Apex or LWC when the requirement needs it (complex logic, heavy volume, integrations, custom UI). Explain that you think about who will maintain it after you, and about testability.

Read the release notes for your clouds, run the preview sandboxes, test critical flows before the release, and follow the Trailhead and community channels. Mention a specific recent feature you tried, because it proves it's a habit.

Ask what problem the business is trying to solve before debating the solution. Offer one or two alternatives, explain the trade-offs (cost, risk, maintenance) in plain words, and agree on what "done" looks like. It shows you're a consultant, not an order taker.

Start with discovery: review the data model, automation (flows, triggers, validation rules), profiles and permissions, integrations and technical debt. Run an org health check, speak to the users, and write down what you find before changing anything. Then fix the risky items first.

Salesforce is like a shared apartment building: every tenant gets a fair share of electricity, so no single tenant can overload the building. Limits make sure one customer's code can't slow everybody else down, which is why we design for efficient, batch-friendly processing.

Order of execution when a record is saved

The short version. The full list is in the Apex Developer Guide.

  1. Load the record and run system validation (required fields, field formats).
  2. Run before-save Record-Triggered Flows.
  3. Run before triggers.
  4. Run custom validation rules, then duplicate rules.
  5. Save the record to the database, but don't commit yet.
  6. Run after triggers.
  7. Run assignment rules, auto-response rules and escalation rules.
  8. Run after-save Record-Triggered Flows.
  9. If a flow or trigger updated the same record, the update cycle repeats (with a limit on recursion).
  10. Update roll-up summary fields and recalculate sharing.
  11. Commit to the database, then run post-commit work such as emails and async jobs.
